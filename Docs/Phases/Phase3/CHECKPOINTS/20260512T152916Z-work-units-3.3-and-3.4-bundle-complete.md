### Decision #17 (UI must not lie about Best-Effort Stop)

The WU3.4 SCOPE.md explicitly says Phase 3 ships `running` and
`completed` from WU3.4; WU3.5 adds `interrupted` and
`alreadyExecuted`. Honoring Decision #17 here means designing
the data + view APIs to accept all four states from the start so
WU3.5 doesn't have to retrofit them. Evidence that this is done:

- `InlineToolCall.Status` has all four cases; `complete()`,
  `interrupt()`, `markAlreadyExecuted()` are mutation methods that
  exist today.
- `StreamingAssistantMessage.update(toolCallID:transform:)` exists
  today as the WU3.5 mutation hook; tested in
  `testUpdateToolCallID_TransformsCallInPlace`.
- `ToolCallCardView` renders distinct icons, badges, border colors,
  and detail banners for all four states. The `.interrupted` and
  `.alreadyExecuted` paths run today (you can construct an
  `InlineToolCall` with those statuses and the view renders them);
  they just aren't produced by the current event pump.

## Decisions Made During This Run

1. **`/v1/runs/{id}/events` for streaming, `/v1/chat/completions`
   retained as the back-stop API.** SCOPE.md called for the switch
   to /v1/runs (WU3.1 Finding 1). The `chatCompletion(...)` method
   on `HermesAPIServerClient` is NOT deleted — it's used by the
   live integration test
   (`HermesAPIServerClientTests.testIntegration_ChatCompletionAgainstRealAPIServer`)
   and may have non-streaming callers in future work units. Removing
   it would expand scope and break the integration test. Keep it
   as available API surface; the streaming path is the new default
   for the chat composer.

2. **Tool-call ID matching: stack-by-name, MOST-RECENT running
   wins.** WU3.1 byte-level evidence shows the `/v1/runs/{id}/events`
   `tool.completed` event carries `tool` (name) and `duration` /
   `error` but NO `tool_call_id`. Strategy: pop the most-recent
   in-flight tool segment whose `toolName` matches. This handles
   sequential tool calls (the common case in the evidence file)
   and degrades to FIFO for pathological parallel-same-name calls.
   Trade-off accepted; flagged for re-evaluation if Hermes adds a
   `tool_call_id` field later (REALITY.md re-investigation).

3. **`StreamingAssistantMessage.Segment` per-text-state.** Each
   text segment owns its own `StreamingMessageState` (the WU3.2
   per-message AST/parse object). The alternative (one shared
   state per message) breaks the inline-tool-card interleaving:
   you'd render text → tool card → text in three separate views
   but feed all three from one AST, which would re-parse the
   later text inside the same AST context as the earlier — wrong
   for streaming. Per-segment state is the right model and
   matches how the user reads the conversation in order.

4. **`.diakMessageAppended(sessionID:)` HermesAction added as a
   reducer no-op for now.** Phase 2 SCOPE.md deferred adding a
   message slice; Decision #8's streaming exception scopes multi-
   window-live-stream out of v1. The action exists so future
   Phase 4/5 work (Diak-as-MCP-server, automation triggers off
   message arrival) can extend the reducer without changing call
   sites. The reducer's no-op handler is explicit (not implicit
   via `default:`) and documents *why* it's a no-op.

5. **Stream cancellation is client-side only for WU3.3.** The
   server-side `POST /v1/runs/{id}/stop` companion is WU3.5's
   responsibility per the SCOPE.md split. WU3.3's `ChatViewModel.stop()`
   cancels the consuming Task; the coordinator surfaces this as
   `.cancelled` and persistence runs through the same finalization
   path with `DiakMessage.Status.cancelled`. No protocol message
   leaves Diak in WU3.3 on cancel; WU3.5 will add it. Tested by
   `RunStreamCoordinatorTests.testConsume_TaskCancellation_*` with
   a timing-tolerant assertion (URLSession may surface the
   cancellation as `.cancelled` or `.interrupted` depending on
   when the request reaches the protocol stack — both honor the
   "no content lost" invariant).

6. **`.secondsSince1970` for JSON encoding of tool calls (not
   ISO8601).** Initial implementation used `.iso8601`; the
   round-trip test surfaced sub-second precision loss because
   ISO8601's default formatter strips fractional seconds. The
   correct choice for preserving `durationSeconds` fidelity across
   the persistence boundary is `.secondsSince1970` (which writes
   the full Double precision). Applied symmetrically to the test
   and to `ChatViewModel.encodeToolCalls`.

7. **Unknown event-type contract: log + skip, no failure
   propagation.** Per Nick's WU3.3 brief: "Graceful degradation on
   unknown SSE event types ... Don't crash the stream. Don't error
   out the run. Just skip the unknown event and continue consuming
   the stream." The `RunEventPayload.decode(from:)` returns
   `.unknown(eventType:, rawData:)` (does NOT throw); the
   `RunStreamCoordinator` invokes its `unknownEventLogger` closure
   (default = OSLog.info entry) and continues the loop. End-to-end
   verified by
   `ChatStreamingIntegrationTests.testStartStreaming_UnknownEventMidStream_StreamSurvives`
   where a `tool.preflight` event interleaves between two
   `message.delta` events and the surrounding text survives.

8. **`StreamingAssistantMessageView` segment caret suppression.**
   Only the trailing text segment shows the streaming caret (per
   SCOPE.md WU3.4 visual contract: "the message stream alongside
   the streaming text"). Earlier text segments are "frozen" once a
   tool card opens between them and the trailing text; suppressing
   their caret keeps the UI honest about where new content is
   landing. Implemented as `showStreamingCaret: isLast && message.phase == .running`.
