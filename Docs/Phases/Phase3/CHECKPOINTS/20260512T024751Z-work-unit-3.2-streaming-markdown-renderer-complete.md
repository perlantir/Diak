## Decisions Made During This Run

1. **Block identity uses position index (`IdentifiedBlock.id =
   blockChildren.firstIndex`).** Per WU3.1 finding 6 and SCOPE.md
   WU3.2: under streaming append, earlier blocks never change —
   only the trailing block receives new content. Index-based
   identity makes SwiftUI's `ForEach` diff trivial: same index
   means same View identity. The `BlockKind` `Equatable` check
   short-circuits re-render for unchanged blocks. Verified by
   `testStreamingCorrectness_EarlierBlocksUnchangedAsTextAppends`.

2. **Value-type intermediate (`BlockKind`) between AST and
   SwiftUI views.** SCOPE.md called for "AST visitor that
   produces SwiftUI views, one per block element." Direct
   visitor-to-View produces a fresh `AnyView` per parse and
   defeats SwiftUI diffing (no Equatable on `AnyView`). The
   intermediate value type makes equality structural and
   block-level — SwiftUI re-renders only when `BlockKind`
   meaningfully changes, not on every parse.

3. **Open-fence detection by line-based scan, not AST
   inspection.** The cmark-gfm AST closes all open fences at EOF
   — there's no native "is this fence closed?" flag. Strategy:
   walk the source for fence-start lines (≥3 of ``` ` ``` or
   `~~~` after up to 3 spaces) and toggle an in-fence flag.
   First pass had a bug (didn't count the final fence run at
   EOF); rewrote with `String.split(separator:)` line iteration
   and now passes all open/closed fence tests.

4. **Highlightr theme: `atom-one-light`.** Diak's chat canvas
   uses `HermesColors.canvas` (warm off-white). Atom One Light
   reads well there. Phase 3 SCOPE.md didn't authorize a theme
   picker UI; one theme picked at construction time and used
   everywhere. Switch to a dark theme via the
   `CodeBlockHighlighter(themeName:)` init if Phase 6 polish
   adds dark mode.

5. **`StreamingMessageState.reset()` added beyond initial
   design.** Originally the state was append-only by design.
   Once I wired the test harness window, "Reset" became a real
   user-facing action — re-creating the `@StateObject` on every
   reset breaks SwiftUI identity. Cleanest fix: explicit
   `reset()` method on the state. Tested via
   `testStreamingCorrectness_ResetClearsTextAndBlocks`.

6. **Pulsing caret as a separate `StreamingCaret` View.**
   SCOPE.md didn't specify; the SwiftUI-natural approach is a
   thin Rectangle that opacity-pulses via `animation()`. Cheaper
   than custom `Text` cursor manipulation and respects
   accessibility. Visible only while `phase == .running`.

7. **Inline runs encoded as a value enum (`InlineRun`) rather
   than building `AttributedString` during parsing.** Two
   reasons: (a) `Equatable` for the SwiftUI-diff guarantee — two
   `InlineContent` values with identical runs are equal even
   when constructed at different times; (b) lazy
   `AttributedString` construction, since the cost of building
   one is only paid when the block actually renders (not when
   it's compared to a previous parse).

8. **Scroll preservation is implemented via a sentinel `Color.clear`
   at the bottom with `onAppear`/`onDisappear` toggling
   `@State isAtBottom`.** The `onContentChange` callback triggers
   `proxy.scrollTo(bottomSentinelID, anchor: .bottom)` ONLY when
   `isAtBottom == true`. If the user has scrolled up, the
   sentinel is off-screen, `isAtBottom == false`, and auto-
   scroll is suppressed. This is the standard pattern used in
   the existing `ChatTranscriptView` (`MessageBlock` rendering
   path); WU3.2 doesn't change the chat transcript yet — that's
   WU3.3.

## Questions for Nick

1. **Visual acceptance for the 50 Hz / 8000-char run.**
   Data-layer evidence is strong (avg 2.5 ms/append, max 3.7 ms,
   well under the 20 ms frame budget). But the SCOPE.md
   acceptance specifically calls out "no visible flicker, dropped
   characters, or scroll jumps" — these are SwiftUI-rendering
   properties XCTest can't verify. **The harness window is
   wired and accessible** in Debug builds via Cmd+Option+Shift+M.
   Suggested verification: launch Diak.app from Debug build,
   open the harness, paste an 8000-char document (the default
   sample is ~2500 chars; the stress test's `makeDocument` shape
   gets you to 8000+), set cadence to 50 Hz, observe rendering
   and scroll behavior. Acceptable to ratify WU3.2 conditional
   on this visual pass?

2. **Highlightr theme.** Chose `atom-one-light` to match the
   warm-canvas palette. Phase 3 doesn't authorize a theme-
   picker UI. If you'd prefer a different theme (Diak might
   look better with a darker code-block contrast), it's a
   one-line change in `CodeBlockHighlighter.init`. OK as-is?

3. **Tilde-fence open detection edge case.** CommonMark §4.5
   says fence character must match (start with ``` ` ``` →
   close with ``` ` ```, start with `~~~` → close with `~~~`).
   My detector enforces this strictly. If a user types `` ``` ``
   to open and `~~~` to close (illegal Markdown), my detector
   says the fence is still open — which matches CommonMark spec
   but might surprise a user. Probably fine for v1; flagging.
