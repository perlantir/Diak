## Decisions Made During This Run

These are *findings*, not architectural commitments — SCOPE.md
(written after this checkpoint ratifies) is the place where
findings get formalized.

1. **`/v1/runs/{id}/events` is the better streaming surface**
   than `/v1/chat/completions` for Phase 3. Cleaner event shape,
   richer tool metadata (duration, error flag), native reasoning
   event, explicit `run.completed` terminator, and the required
   `POST /v1/runs/{id}/stop` companion for the approval flow.
   Phase 1's `runEvents(runId:)` `AsyncThrowingStream` API
   already exists and is tested; WU3.3 inherits it ready.

2. **Markdown renderer: `apple/swift-markdown` + hand-written
   SwiftUI visitor.** Down is abandoned (4.5 years stale);
   MarkdownUI is maintenance-mode as of 2025-12-28 and has
   documented freeze-on-long-docs / EXC_BAD_ACCESS issues.
   Apple's library is actively maintained, has no SwiftUI
   renderer (we write one), and lets Diak control SwiftUI's
   diff scope to per-block — essential for handling 20–50 Hz
   token streaming without view-tree thrash.

3. **Approval pattern: "Best-Effort Stop" (Pattern A-modified).**
   Hermes' API Server has `tool_execution: server` and no native
   approval hook (despite Hermes' `approvals.mode: "manual"`
   config — that config is wired only for CLI/TUI sessions, not
   API). The realistic pattern is opt-in client-side gating
   that races `POST /v1/runs/{id}/stop` against tool execution.
   ~120 ms /stop roundtrip measured live. Works for slow tools;
   surfaces "Already Executed" UX for fast ones. True
   pre-execution gating is deferred to Phase 4 via
   Diak-as-MCP-server.

4. **Streaming state lives outside the Phase 2 reducer.** Token
   chunks arrive at 20–50 Hz; dispatching through HermesState
   would force O(n²) snapshot equality work plus full-tree
   SwiftUI diffs per token. Pattern: per-`ChatViewModel`
   `StreamingMessageState` for the in-flight message;
   `HermesState.dispatch` only at completion (single
   `.diakMessageAppended(...)` action).

5. **Reasoning content is post-hoc on the runs API.** Hermes
   emits a `reasoning.available` event *after* all
   `message.delta` events and *before* `run.completed`. The
   event carries a summary string, not raw step traces. The
   richer reasoning fields (`reasoning_content`,
   `reasoning_details`, `codex_reasoning_items`) are available
   post-run via `/api/sessions/{id}/messages` on the dashboard,
   not streamed.

6. **Hermes' gateway auto-supervises.** `kill -9` on the API
   server PID is followed by an automatic respawn within ~3 s.
   Diak does NOT need to restart the API server process; only
   needs to reconnect the SSE stream and surface "stream
   interrupted" to the user.

## Questions for Nick

1. **Confirm the Phase 3 surface commitment.** REALITY.md
   recommends `/v1/runs/{id}/events` over `/v1/chat/completions`.
   This is a bigger surface (Diak owns run lifecycle, not just
   "send prompt → get reply") but unlocks the approval flow,
   reasoning event, and cleaner tool events. Phase 1's
   `HermesAPIServerClient.runEvents` is already built; WU3.3
   migrates `ChatViewModel` to use it. OK to commit in SCOPE.md?

2. **Confirm the "Best-Effort Stop" approval pattern.** It
   doesn't actually gate fast tools — a `rm -f` invocation will
   land before our /stop arrives. The UX shows "Already
   Executed: rm" as a warning rather than blocking. For
   destructive-tool safety, the recommendation is to rely on
   *Hermes-side toolset configuration* (don't enable the
   `terminal` tool in toolsets the user doesn't want
   un-approved). Phase 4 adds Diak-as-MCP-server for true
   gating. Is this UX acceptable for the v1 ship?

3. **One Hermes config caveat.** During the dropped-connection
   probe, I `kill -9`d PID 37056 (the gateway). It respawned
   automatically. No state was lost beyond the in-flight run,
   and Hermes' state is whatever it was. Confirming this is OK
   — the alternative would have been to use a curl client-side
   abort instead, which doesn't exercise the same TCP semantics
   from Diak's `URLSession.bytes` perspective. Per the WU3.1
   prompt this was authorized; flagging just in case.

4. **Markdown renderer scope.** REALITY.md proposes ~200–400
   LOC for a swift-markdown SwiftUI visitor covering
   paragraphs, headings, lists, code blocks (Splash for
   highlighting), tables, blockquotes, inline emphasis/code/
   links. Is the syntax-highlighting integration in-scope for
   WU3.2 or deferred to a polish unit?

## Out-of-Scope Items Observed

- **Hermes' API Server doesn't honor `approvals.mode`.** Found
  during the Pattern (b) evaluation. The Hermes-side fix
  (wire `set_approval_callback` in `api_server.py`) is upstream
  work, not Diak's. Documented in REALITY.md Area 4. Phase 4's
  Diak-as-MCP-server path makes this moot for Diak's needs.
- **The dashboard's chat plugin probably renders these same
  events.** Area 5's background agent will look at the
  dashboard SPA's tool-call rendering as a reference pattern. If
  it doesn't, future work can do that investigation.
- **Hermes can stream reasoning via `/v1/responses` (OpenAI
  Responses API).** Capabilities probe shows
  `responses_streaming: true`. Not investigated in WU3.1
  (Phase 3 likely doesn't need it; chat/completions and runs
  cover the surface). If Phase 5/6 polish wants real reasoning
  traces, the Responses API is the place to look.
- **`/v1/runs/{id}/stop` actual subprocess kill semantics**
  were not probed at the OS level. The event stream emits
  `run.cancelled` ~120 ms after stop; whether the
  Hermes-side subprocess is SIGKILL'd or orphaned is implementation
  detail to confirm during WU3.5 implementation.
- **Tool argument retrieval.** The
  `event: hermes.tool.progress` `running` payload includes a
  `label` field (a human-readable preview like
  `"/tmp/sse_a_simple.sh"` or `"python3 - <<'PY' print(47*23) PY"`)
  but NOT the structured argument JSON the model passed to the
  tool. If Phase 3 wants to show the raw arguments in a
  tool-call card's expandable detail, the data isn't in the
  SSE stream — it'd come from the post-run
  `/api/sessions/{id}/messages` query on the dashboard.
- **Streaming + multi-window-live-stream.** Phase 3 explicitly
  scopes this OUT: only the active composer's window sees the
  in-flight stream. Other windows see the completed message.
  If a future phase wants live-stream multi-window, the
  `StreamingMessageState` would migrate up into a shared
  parent (or join `HermesState` with a different update
  pipeline).
