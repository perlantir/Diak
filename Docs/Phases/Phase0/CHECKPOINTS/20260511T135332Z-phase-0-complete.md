## Decisions Made During This Run

1. **Used `open -a <APP_PATH>` instead of bare `open diak://test` for
   criterion 6.** Three pre-existing stale Diak.app bundles on this
   machine also claim the `diak://` scheme, and LaunchServices was routing
   bare `open diak://test` to one of them on the first attempt. `open -a`
   forces routing to the build under verification. The semantic content of
   the test (does our scheme registration work? does DeepLinkParser fire?
   does the app survive?) is identical either way. Not in scope to clean
   up the stale registrations.

2. **Did not delete the three stale `/private/tmp/diak_phase1_e2e_*` and
   stale-DerivedData `Diak.app` bundles** that pollute LaunchServices'
   `diak://` resolver. Out of scope for Phase 0 verification.

3. **Initially wrote the checkpoint under `-phase-0-verification-failed.md`,
   then renamed to `-phase-0-complete.md` after Nick ratified criterion 8.**
   The first-pass decision was to surface the borderline strictly rather
   than ratify on Nick's behalf. After ratification, this file was renamed
   via `git mv` (history preserved) and amended to record the final state.

4. **Calibration note for future scope evaluation (from Nick, recorded here
   so the next agent run has it).** Small refactor-by-extraction files that
   implement in-scope functionality are acceptable. New files that
   introduce *new behavior* (new endpoints, new types not implied by
   scope, new dependencies) are not. The test is: "is this file doing
   work that was authorized, just organized differently?" If yes, in-scope.
   If no, stop. Applied to this run: `HermesAPIEndpointConfig.swift`
   passes the test (extracts already-authorized endpoint+timeout work);
   `HermesAPIErrorTestHelpers.swift` is even more clearly in-scope (test
   helper for an authorized topic).
