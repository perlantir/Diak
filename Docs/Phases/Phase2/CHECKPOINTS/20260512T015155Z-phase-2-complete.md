## WU2.3 — Polling Layer + Token Rotation (distinct section)

### What landed
- `TokenEpochObserver` (MainActor class, weak ref to HermesState):
  - On every `.supervisorHealthChanged` emission, forwards to
    reducer.
  - On `.running(_, _, token: T_new)` where `T_new` differs from
    the previously-seen token, dispatches
    `.tokenRotated(newEpoch: currentEpoch + 1)`.
  - First `.running` is **not** a rotation (no previous token);
    subsequent rotations advance the epoch monotonically.
- `HermesPollingCoordinator` (MainActor class, owns 8 endpoint
  tasks):
  - Per-endpoint async loop: capture epoch → fetch → diff →
    dispatch (or `.pollError`) → backoff-aware sleep.
  - Health-driven spawn/cancel: tasks only exist while
    `supervisor.health == .running`. Transition away cancels
    all tasks; return to `.running` spawns fresh ones.
  - Backoff: `min(base × 2^N, maxBackoff)` per consecutive
    failure; success resets the counter.
- `liveFetcher` factory: builds the production fetcher closure
  that wires the dashboard client into the diff+dispatch
  pipeline. One `case` per endpoint; each case fetches, compares
  to the current slice via `Equatable`, dispatches only on
  observable change.
- Production wiring in `HermesDesktopApp`: coordinator started
  inside the `.task { ... }` block, stopped on
  `willTerminateNotification`.

## Decisions Made During This Run

1. **Bundle did not split at the WU2.3 boundary.** Per SCOPE.md
   escape clause: evaluated and rejected. The polling layer and
   the Diak-emission layer both run on `@MainActor` and dispatch
   through the same reducer; no infrastructure divergence
   surfaced.

2. **Polling coordinator uses MainActor-isolated tasks rather
   than a dedicated polling actor.** WU2.2 used `@MainActor` for
   HermesState. Spawning polling tasks on the main actor keeps
   dispatch + diff comparison serialized with reducer mutations
   — no actor hops, no Sendable boundary headaches. Network I/O
   awaits release the main actor's executor as needed; this is
   stock async/await Swift behavior.

3. **Sleeper closure type is `@MainActor` rather than `@Sendable`.**
   The first iteration used `@Sendable (TimeInterval) async throws
   -> Void`. Tests that captured a non-Sendable
   `RecordingSleeper` triggered a data race
   (`UnsafeMutablePointer.initialize overlapping range`) when
   multiple endpoint tasks called the sleeper concurrently. Fix:
   declare the closure `@MainActor`. Production's
   `Task.sleep(nanoseconds:)` call works fine on MainActor
   (Task.sleep is non-isolated and respects the caller's executor).

4. **VMs keep `@Published` typed-projection mirrors of state
   slices rather than retiring them outright.** SCOPE.md
   acceptance #3 said view-model `@Published` ivars become
   "computed projections OR get retired entirely." The chosen
   form: `@Published` mirrors that hold the legacy view-shape
   (`[HermesSession]`, `[HermesSkill]`), populated via Combine
   subscription on the corresponding state slice's
   `HermesDashboard*` shape. This means a source grep for
   `@Published var sessions` still finds the VM line — but the
   intent of acceptance #3 (VMs READ from HermesState, never
   WRITE) holds. Alternative (views consume
   `HermesDashboardSession` directly) requires significant
   view-layer churn and would extend Phase 2 into Phase-3-
   adjacent work; deferred.

5. **Test count landed at +27, below the SCOPE band of +30–60.**
   Cause analysis: the four race policies were exhaustively
   covered in WU2.2's `HermesReducerTests` (28 tests, including
   per-action and per-policy). WU2.3+2.4's new tests focus on
   the *coordination + wiring* layer rather than re-asserting
   reducer invariants. Coverage of each WU2.3+2.4 acceptance
   criterion has at least one dedicated test:
   - Pause/resume: 2 tests
   - Backoff: 3 tests (math + interleaved-across-endpoints)
   - Diff-before-dispatch: 1 test (production fetcher)
   - Token rotation: 6 tests
   - Diak-store → state bridge: 4 tests
   - Multi-window propagation: 3 tests
   - External Hermes change: 1 test (live)
   - VM-level dispatch: 5 tests
   Adding 3+ more tests to hit the band would mostly be
   duplication. Flagging in checkpoint per SCOPE.md.

6. **Coordinator's `liveFetcher` reads `hermesState` strongly
   (not weakly).** Lifetime of the coordinator is tied to the
   App's `@StateObject` — `hermesState` and the coordinator
   both die when the App exits. Weak capture would force `?`
   handling at every fetcher branch with no real benefit.

7. **`endpoint` retired as `let`, not removed entirely.**
   `HermesEngineSettingsView` displays the URL so users can
   verify it. Removing the property would force a view-layer
   change (drop the section entirely). The `let` form retains
   the display while ruling out future drift.

8. **Bounded ring on `phase2Errors` survives WU2.3.** Errors
   from `pollError` and `userRefreshFailed` are dispatched
   through the reducer's existing `appendError` helper, which
   caps at `phase2ErrorRingCapacity = 32`. No new ring logic
   needed in the coordinator.

- **`@Published var skills` and `@Published var sessions`

  not actually a Phase 3+ blocker but worth a note. Phase 3's
  view rewrites for chat/approvals are the natural place to
  decide whether to consume HermesState slices directly in views
  and retire the VM projections.
- **`HermesEngineViewModel.restartState` and `reconnectState`
  remain VM-local @Published action markers.** SCOPE.md offered
  "replace with derived `HermesState.inFlightActions`" as an
  alternative. No cross-view consumer needs that visibility in
  Phase 2; keeping them view-local is the minimal change. If
  Phase 5 (autonomous safety gates) needs a global "is anything
  running" indicator, this is the place to revisit.
- **`HermesPollingCoordinator` doesn't currently emit
  `.userInitiatedRefresh` itself.** That dispatch lives in the
  VMs' `refreshViaState` methods. Architecturally consistent
  (the coordinator is the *poll* origin; user-initiated refresh
  is the *VM* origin), but worth flagging that two separate
  code paths now build action sequences for the same endpoint.
- **`pollingCoordinatorHolder` exists only to satisfy
  `@StateObject`.** A side-effect-only orchestrator with no
  `@Published` properties; the holder is pure SwiftUI ownership
  ceremony. If a future SwiftUI version supports direct
  `@State` of non-ObservableObject classes for the App scene,
  the holder can go away.
- **`ContentRouter` and `AppShellView` initializers grew an
  extra parameter (`hermesState`).** Mechanical threading from
  the App through the view hierarchy. No injection container or
  environment-key indirection added; explicit is fine for a
  surface this size.
- **Phase 1's `URLSessionHermesAPIClient` test suite (M3/M4/M5/M6)
  still runs.** Still using the bridge-shape mock fixtures. Per
  Phase 1 WU6 status: those retire in Phases 3-5 alongside their
  consumers. Not touched in Phase 2.
- **SwiftData `ModelContext.willSave`/`didSave` not used.**
  SCOPE.md mentioned hooking those as "the free reactive
  primitive." On inspection, SwiftData's notification surface is
  undocumented and quirky; the direct-dispatch approach inside
  `DiakSessionStore`'s CRUD methods is deterministic, explicit,
  and doesn't depend on framework internals. Same observable
  outcome.
