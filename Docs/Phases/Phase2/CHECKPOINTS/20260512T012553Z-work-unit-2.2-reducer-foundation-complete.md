## Decisions Made During This Run

1. **Retired the vestigial Phase 1 HermesState fields.** WU2.1
   confirmed zero readers/writers for `daemon`, `messages`,
   `approvals`, `evidence`, `connectors`, `automations`, `memory`,
   the Phase-1-shape `sessions/skills/config`. The ratified
   SCOPE.md redefined the namespace with Phase 2 types of the same
   names (`sessions: [HermesDashboardSession]`, etc.), which
   structurally requires retiring the Phase 1 ones. This is in-scope
   per SCOPE.md, not a scope expansion (CLAUDE.md prohibition #11
   considered explicitly; the property list ratified in SCOPE.md was
   the dispositive authority).

2. **`HermesStateSnapshot` uses `Equatable` rather than `Hashable`.**
   Two of the dashboard types (`HermesDashboardConfig`,
   `HermesDashboardModelInfo`) are `Equatable` but not `Hashable` —
   Phase 1 didn't need their hashability, and adding it would have
   been an out-of-scope edit to Phase 1 surface. Snapshot equality
   is the only property dispatch needs.

3. **Snapshot-equality short-circuit on `dispatch(_:)`.** Race
   policy 4 (dedup duplicate health changes) requires the reducer
   alone is *not* enough: `@Published` would still emit
   `objectWillChange` on identical-value assignment. So
   `dispatch(_:)` compares the new snapshot against the current
   one and skips the apply step entirely when equal. This preserves
   the policy at the *observable* layer, which is what WU2.4
   subscribers care about.

4. **Snapshot decomposition pattern.** `HermesState.apply(_:)` does
   per-field "set only if different" rather than blanket re-assign.
   Belt-and-braces: combined with the dispatch-level snapshot-equality
   short-circuit, no spurious `@Published` emissions can occur even
   if a future code path bypasses `dispatch(_:)`.

5. **DaemonStatusViewModel derives status via Combine on
   `$dashboard + $supervisorHealth + $currentEpoch`.** Tried
   `objectWillChange.sink` first; that publisher fires *before* the
   property updates (willSet semantics), and reading
   `hermesState.dashboard` inside the sink closure would observe the
   old value. CombineLatest on the typed `$` publishers receives the
   new values directly as closure arguments — correct semantics and
   no race against the publishing order.

6. **Supervisor → HermesState bridge lives in
   `HermesDesktopApp.swift`, not in `HermesState` itself.** Keeping
   `HermesState` un-coupled to `HermesProcessSupervisor` preserves
   reducer purity and matches the Phase 2 design — the *App* is the
   composition root; the reducer doesn't know about supervisor
   types.

7. **Bounded error ring capacity of 32 (`phase2ErrorRingCapacity`).**
   Arbitrary but defensible: with the WU2.1-validated 2s/10s/60s
   polling cadence, one error per second on a single endpoint would
   fill the ring in ~30 seconds — enough scrollback for the
   Inspector pane (Phase 3) to render the recent failure burst,
   not so much that the buffer grows unbounded across a long
   session. Cap is exposed as a public constant so tests pin to
   it and Phase 3 can re-tune without source diving.

## Recommendation for Next Work Unit

Ratify WU2.2 and proceed to **WU2.3+WU2.4 bundle: Polling Coordinator
+ View-Model Migration**, per Phase 2 SCOPE.md.

WU2.3 builds `HermesPollingCoordinator` that owns the three-tier
2s/10s/60s cadence per endpoint, emits `.<endpoint>Observed(payload,
epoch: snapshotEpoch, source: .poll)` and `.pollError(...)`. It uses
the supervisor's *current* token epoch (read from
`hermesState.currentEpoch`) at the moment a request is *issued* and
attaches it to the resulting action — the reducer drops anything
arriving on a stale epoch automatically.

WU2.4 migrates the remaining Hermes-owned view models
(`SessionsViewModel`, `SkillsViewModel`, `SettingsViewModel`, the
relevant slice of `HermesEngineViewModel`) to read from `HermesState`
slices via the same Combine pattern DaemonStatusViewModel now uses.
Their `refresh()` methods become `dispatch(.userInitiatedRefresh(...))`
calls; the user-wins race policy then handles the click-while-polling
case automatically.

The supervisor → `tokenRotated` bridge — currently absent — should
be added in WU2.3 alongside the polling coordinator. When the
supervisor's `health` transitions to a new `.running(_, _, token:)`
with a different token than the previous `.running` state, the App
should `dispatch(.tokenRotated(newEpoch: increment))` to invalidate
in-flight observations issued under the old token. Without this,
race policy 1 (token epoch) is structurally inert because nothing
ever bumps `currentEpoch`. Note for WU2.3 SCOPE additions.
