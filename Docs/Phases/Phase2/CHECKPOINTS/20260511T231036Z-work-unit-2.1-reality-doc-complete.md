## Questions for Nick

Three observations from the investigation that are *informational*
for Phase 2 SCOPE.md authoring; none block ratification of WU2.1.

**Q1. Should Decision #8 in PROJECT_STATE.md be updated to reflect
that HermesState is currently vestigial?** Decision #8 today reads
"Single source of truth for Diak-owned state: HermesState. Diak
owns ... HermesState caches a projection [of Hermes-owned state]."
The investigation found that HermesState is declared and injected
but has zero readers and zero writers. Two ways to update:

- (a) Leave Decision #8 alone, treat Phase 2 as the work that
  **makes** Decision #8 true. The decision describes the target
  state, not the current state.
- (b) Amend Decision #8 to explicitly note "as of Phase 1, this
  is a target architecture; Phase 2 wires it in" so future
  agents reading PROJECT_STATE.md don't get confused by the gap
  between the doc's framing and the code reality.

Either is fine. Surfaces for awareness; PROJECT_STATE.md is your
file to edit.

**Q2. Phase 2 SCOPE.md will need to pick polling cadences for
each endpoint.** The cost-tier breakdown in REALITY.md Area 2 is
a defensible starting point but the *interesting* design question
is what the heartbeat tier actually is (1 s? 2 s? 5 s?), which
trades freshness for steady-state load. The PROJECT_STATE.md
acceptance ("external Hermes change reflects in Diak within 5
seconds") gives the upper bound; the lower bound is taste. Worth
naming a default in SCOPE.md so the polling layer doesn't need an
ad-hoc decision.

**Q3. The reducer's race policy (poller-vs-user-action, stale-
read-after-local-mutation) is a design choice WU2.1 surfaces but
doesn't decide.** The provisional Phase 2 plan you mentioned
(4 work units, with WU2.3+2.4 pre-authorized for bundling) likely
covers this. Worth being explicit in SCOPE.md about which work
unit owns the race-policy decisions so they're not invented
inconsistently per view model.
