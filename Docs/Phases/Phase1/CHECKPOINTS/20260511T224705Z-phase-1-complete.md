### Path B locked-in architecture

After Phase 1, the runtime topology matches Decision #13 precisely:

- **Inference** goes through `HermesAPIServerClient` →
  `POST :8642/v1/chat/completions`. Persistent Bearer auth from
  Keychain. Diak's chat composer is the only inference caller in
  Phase 1; Phase 2/3 expand to streaming + tool-call UI.

- **Hermes-self-management surface** (sessions list, skills list,
  config snapshot, daemon status, profiles) goes through
  `HermesDashboardClient` → `:9119/api/*`. Ephemeral Bearer token
  scraped from SPA HTML via `DashboardTokenScraper`. Token rotation
  across dashboard restarts is transparent to callers (TokenProvider
  closure re-reads supervisor.health on every request).

- **Diak-owned features** (approvals, Composio connectors,
  automation builder, memory dashboard) are explicitly disconnected
  from any client in Phase 1. View placeholders cite the phase
  they land in (3/4/5). Diak's own SwiftData store (DiakSessionStore
  + WU5 models) is the first piece of the Diak-owned data plane;
  Phases 3-5 add `DiakApproval`, `DiakConnector`, `DiakAutomation`,
  `DiakMemoryItem` model families on the same store.

### Carried into Phase 2 / Phase 3

Debt the Phase 2 (Diak-Side Reactive State) and Phase 3 (Chat plus
Canvas) teams should be aware of:

1. **Chat view-shape projection.** ChatViewModel maps DiakMessage →
   HermesMessage one-way for the views. Phase 3 chat work should
   either migrate ChatTranscriptView / MessageBlock to DiakMessage
   directly OR build a HermesState reducer that owns the shape
   conversion (Phase 2 territory). Currently the projection is
   inline in ChatViewModel.

2. **Settings UI is sparsely backed.** The Hermes dashboard's
   `/api/config` exposes a flat shape; the bridge-era SettingsView
   expects a rich nested shape (profiles + providers + tools +
   security + daemon). Phase 1 fills profiles + daemon; providers
   + tools + security stay empty. Phase 4 should either trim the
   Settings UI to what the dashboard actually exposes OR widen the
   HermesDashboardConfig type to match (and update the dashboard's
   side to return more fields, which may need an upstream Hermes
   PR).

3. **Skill toggle is read-only.** The dashboard exposes
   `PUT /api/skills/toggle` per REALITY.md; Phase 1 didn't wire it.
   Phase 4 (Skills, Connectors, OAuth) should add `toggleSkill()`
   to HermesDashboardClient.

4. **Config save is read-only.** The dashboard exposes
   `PUT /api/config`; Phase 1 didn't wire it. Phase 4 should add
   `updateConfig()` to HermesDashboardClient.

5. **Approvals view model still wired to MockHermesAPIClient.**
   ApprovalsViewModel is referenced from non-disconnected sites
   (ChatTranscriptView inline filter, InspectorView). Phase 3
   should replace it with a Diak-native ApprovalsStore (Diak owns
   approvals per Decision #13) and disconnect from MockHermesAPIClient.

6. **Streaming chat composer.** Phase 1 uses non-streaming
   `/v1/chat/completions`. Phase 2 should switch to either
   `/v1/chat/completions` with `stream: true` (token chunks) or
   `/v1/runs` + `/v1/runs/{id}/events` (lifecycle events). Choice
   depends on what the live API Server actually emits (verifiable
   once API_SERVER_ENABLED=true on Nick's machine).

7. **Live chat integration test.** The end-to-end test that sends
   a real prompt to the API Server and verifies the response stays
   XCTSkip'd until Nick enables `API_SERVER_KEY`. Per Q3 of the WU6
   session-2 plan, Nick will enable it after this checkpoint is
   ratified; the test then runs and the Phase 1 ratification
   includes the live result.

8. **Foundation AsyncLineSequence pitfall** is now documented in
   PROJECT_STATE.md's Known Issues + a "DO NOT SIMPLIFY" comment
   in HermesAPIServerClient. No code action needed in Phase 2.

## Decisions Made During This Run (WU6 session 2)

1. **No new top-level Swift classes.** The "one new top-level class
   authorized" budget Nick granted was not used. All wiring fits
   inside existing types via `init(dashboardClient:)` overloads or
   nested helpers.

2. **Adapter-at-view-model not at protocol.** Per Nick's "no adapter
   pattern wrapping the new clients in the old protocol" rule, the
   view models internally map dashboard types → legacy view-shape
   types. The HermesAPIClient protocol isn't touched. The mapping
   is a view-model implementation detail, not a wire-format adapter.

3. **Diak-owned views are placeholders, not stubs.** Per Nick's
   direction. AutomationsView/ConnectorsView/MemoryView/ActionCenterView
   are now ~10-line SwiftUI views that render EmptyStateView with
   "Coming in Phase X" copy. No view models behind them.

4. **DaemonStatusViewModel kept its name.** Nick authorized
   renaming to HermesEngineStatusViewModel; I didn't take that
   option to minimize call-site churn. Phase 2 can do the rename
   as part of the broader HermesState reducer work.

5. **SettingsView kept its full UI; data is sparse.** Rather than
   rewriting SettingsContainerView + 6 sub-views (BetaReadiness,
   ModelsProviders, ProfileSettings, SecurityPrivacy,
   ToolsPermissions, HermesEngineSettings), I left the UI intact
   and produce a sparse HermesConfigSnapshot from dashboard data.
   The complex edit forms render their empty states (no providers,
   no tools, etc.); the surfaces that have real data (daemon
   status, profiles list, model name) show real Hermes data. This
   is debt #2 above.
